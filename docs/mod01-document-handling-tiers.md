# MOD-01: 업로드된 공고문 처리 3단계 (2026-09-01)

전제: 사용자가 임의의 공고문 PDF를 업로드하는 방식 (희찬/운영자가 미리 정해둔 카탈로그가
아님). 그래서 "처음 보는 기관·상품"이 런타임에 그대로 들어올 수 있다는 걸 전제로 설계.

## Tier A — 아는 유형 (지금은 SH 장기전세주택), 파싱 결과가 기대 형태와 맞음
→ 규칙기반 파서(공급방식×면적구간 브랜치)로 구조화 → program.ts 스키마로 변환 →
자격판정·배점 엔진 정상 실행. (근거: `sh-jangi-jeonse-format-consistency.md`)

### 구현 현황 (2026-09-01, `src/parser/sh-jangi-jeonse.ts`)

파이프라인: `scripts-py/pdf_to_text.py`(pdfplumber로 페이지별 텍스트+표 JSON 추출, LLM
없음) → `src/parser/sh-jangi-jeonse.ts`(섹션/표 헤더를 앵커로 구조화, 못 찾으면 절대
추측하지 않고 `HousingProgram.parseWarnings`에 기록). 49차·50차 실제 PDF로 검증 완료,
스크린샷으로 확인해둔 원본 수치와 전부 일치:

- ✅ 메타데이터(회차, 공고일), 소득기준표(가구원수×%구간 11개), 자산기준표(기본/①/②③
  3열, 총자산·자동차), 신생아 소득·자산 가산 3종, 배점표(일반공급 일반 5/6항목,
  주거약자 3/5항목 — 범주형 2개 제외), 재계약 감점(-6/-4/-2) — 전부 자동 추출값이
  ground truth와 정확히 일치.
- ✅ **EligibilityTrack(면적×공급방식별 신청자격/순위 표)**: 49차·50차 각각 18개 트랙
  (공사건설형 9 + 매입형 9) 정확히 추출, `IncomeThresholdTable` 6개(it-70/-70-dual/
  -105/-140-dual/-150/-200-dual)로 중복 제거해서 연결. 표 헤더를 `신청면적`+`순위`
  고정 텍스트로 앵커링(신생아 가산표·우선공급표와 헤더 모양이 달라 자연스럽게 구분됨),
  공급방식은 표 앞에 나온 마커("공사건설형(일반...)"/"서울시 매입형(일반공급)")를
  따라가되 페이지가 넘어가도 마지막 상태를 유지하도록 처리.
  - **가장 중요한 안전장치**: "소득 외 기준" 셀이 "N순위 미해당자", "그 외 ..." 같이
    *이전 순위를 참조하는 표현*이면(예: "1순위 미해당자 (단, 약정납입회차 6회 이상
    우선)") 절대 `savings-account{minInstallments:6}` 같은 확정 조건으로 잘못 해석하지
    않고, 항상 `custom`(needs-review) 조건으로 남긴다. 초기 구현에서 이 가드가 없어서
    "6회 이상"을 하드 게이트로 오추출하는 버그가 있었는데(정상적인 2순위 지원자가
    실제로는 자격이 있는데도 배제될 뻔함), 원문 대조로 직접 잡아서 수정함 — 49차·50차
    둘 다 재검증 완료.
- ⚠️ 알려진 갭(항상 `parseWarnings`로 표시됨, Tier B로 취급):
  1. **사회취약계층·장애인 항목**: 배점 구간이 순서형 수치가 아니라 범주(matchesAnyOf)라
     자동 추출 대상에서 의도적으로 제외 — 사람 확인 필요.
  2. **⑤-2(85㎡초과 1순위 청약예금 가입기간) 항목**: `pdfplumber.extract_tables()`가 이
     행을 표 경계 인식 실패로 통째로 빠뜨림(추측이 아니라 실측 확인 — extract_text()엔
     있는데 extract_tables()엔 없음). 일반공급(일반) 배점표가 6개 미만으로 나오면 자동
     경고.
  3. **EligibilityTrack 중 "미해당자"/"그 외"/청약예금 예치기준금액 참조 행**: 매
     회차마다 8개 안팎 트랙이 여기 해당(구조상 항상 존재 — 순위 표 자체가 "이전 순위
     탈락자" 형태로 설계돼 있음). 전부 `custom` 조건 + 원문 텍스트로 `parseWarnings`에
     남아 사람이 확인해야 자격판정에 태울 수 있음.
- `HousingProgram.verifiedBy`에 `"rule-parsed"`를 추가(program.ts) — `"manual"`(51차)과
  구분해서 신뢰도를 다르게 취급할 수 있게 함. `parseWarnings`가 비어있지 않으면 그대로
  엔진에 태우지 않고 사람이 확인해야 한다.

## Tier B — 아는 유형인데 이번 문서 파싱 결과가 기대 형태와 안 맞음
예: 배점표 항목 개수가 다르다, 표 헤더가 못 찾은 형태다 등 — 드리프트인지 파싱 버그인지
불확실한 경우. 이때만 사용자에게 "이전 회차 공고문도 첨부해주시면 비교해서 확인하겠습니다"
요청 — **이건 드리프트 디버깅용이지, 새 유형을 이해하기 위한 용도가 아님** (새 유형
이해에는 최소 한 번 사람이 읽고 구조를 매핑하는 과정이 필요하며, 그건 Tier C가 아니라
로드맵 상에서 별도로 처리).

## Tier C — 처음 보는 기관/상품 (예: LH, SH의 다른 상품)
**사람 검토 없이, 즉시 사용자에게 응답.** 억지로 표를 해석해서 자격판정을 시도하지 않는다
— 표 구조를 모르는 상태에서 계산한 값은 "그럴듯하지만 틀릴 수 있는" 결과라 가장 위험하다.

- 보여주는 것 (기관·상품 구조를 몰라도 범용 패턴으로 뽑을 수 있는, 리스크 낮은 정보):
  공고 제목, 발행기관, 공고일/접수기간 등 날짜, 문의처(전화번호), 주택 위치/주소,
  원문 PDF. 실패 시 해당 필드는 그냥 비워둔다(추측 금지 — 프로젝트 전체 원칙과 동일).
- 절대 계산하지 않는 것: 자격판정(신청 가능/불가), 배점. 이 섹션만
  `"이 유형(발행기관/상품명)은 아직 자동 판정을 지원하지 않습니다. 순차적으로
  반영하겠습니다."` 로 대체.
- 사람 개입은 여기서 발생하지 않는다 — 새 유형 지원은 운영자가 별도로 결정하는
  로드맵 작업(51차를 손으로 구조화했던 것과 같은 과정)이지, 업로드 시점에 자동으로
  트리거되는 리뷰 큐가 아니다.
- (향후 아이디어, 지금 구현 안 함) Tier C로 빠진 업로드를 조용히 로그만 남겨두면
  다음에 어떤 기관·상품을 우선 지원할지 판단하는 데 쓸 수 있음.
